# nixos-config

## Making a change

1. Edit the relevant file (see **Layout** below for which one).
2. Apply it on the machine you're sitting at:
   ```
   sudo nixos-rebuild switch
   ```
   `/etc/nixos` is a symlink to this repo on every machine (see **Machines**),
   and `nixos-rebuild` auto-selects `nixosConfigurations.<hostname>` when
   `--flake`/`#attr` are omitted — so no flags needed on either machine. If
   it fails, nothing on the running system changes — fix the error and try
   again.
3. If it worked and you're happy with it, commit:
   ```
   git add -A
   git commit -m "describe the change"
   ```

That's the whole loop. Nothing here needs a reboot except kernel/driver
changes (rare); `switch` takes effect immediately for everything else.

Before committing something non-trivial, it's worth running:
```
nix flake check   # catches eval errors in both hosts' configs
nix fmt           # auto-formats every .nix file
```

## Layout

- `flake.nix` — inputs (`nixpkgs` stable, `nixpkgs-unstable`, `nixos-cosmic`)
  and one `nixosConfigurations` entry per machine, sharing the same base
  module. Also defines the `formatter` and `devShells.default` used by the
  tooling below.
- `configuration.nix` — the entire system + user config: packages, locale,
  services. There's no `home-manager` and no user/system split
  here (removed deliberately — see below); it's all plain NixOS options.
  Does not touch COSMIC at all (see **COSMIC settings** below).
- `hosts/<name>/default.nix` — per-machine config: hostname + anything
  specific to that box.
- `hosts/<name>/hardware-configuration.nix` — machine-specific, autogenerated
  by `nixos-generate-config`.

## Machines

- `nixos` — the original machine (Intel CPU).
- `t14` — ThinkPad T14 (AMD Ryzen AI 350).

On each machine, `/etc/nixos` is a symlink to this repo (the original
installer-generated files are backed up alongside it, e.g.
`/etc/nixos.orig-20261026`):
```
sudo mv /etc/nixos /etc/nixos.orig-<date>
sudo ln -s ~/nixos-config /etc/nixos
```
Since each machine's hostname matches its `nixosConfigurations.<name>`
attribute, plain `sudo nixos-rebuild switch` picks the right one
automatically. The explicit form still works and is needed to target the
*other* machine's config from here (e.g. to sanity-check it builds without
switching to it):
```
sudo nixos-rebuild switch --flake ~/nixos-config#nixos
# or
sudo nixos-rebuild build --flake ~/nixos-config#nixos   # build only, don't switch
```

A nicer alternative is [`nh`](https://github.com/nix-community/nh) (installed
via `configuration.nix`), which shows a readable diff of what's changing:
```
nh os switch ~/nixos-config#<machine>
```

## COSMIC settings

COSMIC isn't managed by this repo, or by Nix, at all — deliberately.
`~/.config/cosmic` is its own plain git repo (`git init`, no symlinks, no
Nix involvement):

```
cd ~/.config/cosmic && git status
```

Every COSMIC setting — shortcuts, panel, theme, wallpaper — is a real file
COSMIC reads and writes directly. Change one via the Settings GUI or by hand,
`git status`/`git diff` in that directory shows it immediately, `git commit`
whenever you're happy with it, `git checkout`/`git revert` if you're not.
Nothing here needs `nixos-rebuild switch`, and nothing in `nixos-config`
needs to change for a COSMIC settings change — the two are unrelated repos
on purpose.

This earlier went through two more complicated stages before landing here:
Nix-declared options via `cosmic-manager` (typed, but every GUI change got
silently reverted on the next `switch`), then an out-of-store symlink from
inside `home.nix` pointing at a file in `nixos-config` (two-way sync, but
still coupled to home-manager's activation and `nixos-rebuild`). Plain `git
init` in place is simpler than both: no reproducibility-from-nothing on a
fresh machine (a new install starts with COSMIC's defaults until you clone
this separate repo over `~/.config/cosmic`), but zero indirection and zero
coupling to the Nix rebuild lifecycle.

## Editor setup

`configuration.nix` installs `nixd` (Nix language server), `nixfmt`,
`statix` (linter), `deadnix` (finds unused bindings), and `nh`.
`.vscode/settings.json` points VS Code's Nix extension at `nixd`, configured
to evaluate this flake's actual options — so hovering/autocompleting inside
`configuration.nix` shows real option docs.

A `.envrc` (`use flake`) is also included: with `direnv` installed and its
VS Code/shell integration enabled, entering this directory automatically
gets you `nixd` & co. on `$PATH` even before you've run `switch` on a new
machine.

## Updating inputs

Bumps `flake.lock`, then rebuild:
```
nix flake update --flake ~/nixos-config
sudo nixos-rebuild switch
```

## Adding a new machine

1. Boot a NixOS installer on the machine, partition/mount disks, then run:
   ```
   nixos-generate-config --root /mnt
   ```
2. Create `hosts/<name>/` in this repo and copy the generated
   `hardware-configuration.nix` into it.
3. Add a `hosts/<name>/default.nix`:
   ```nix
   { imports = [ ./hardware-configuration.nix ]; networking.hostName = "<name>"; }
   ```
4. Add `nixosConfigurations.<name> = mkHost ./hosts/<name>/default.nix;` in `flake.nix`.
5. Point `/etc/nixos` at this repo on the new machine (see **Machines**), so
   `nixos-rebuild switch` auto-selects `nixosConfigurations.<name>` by
   hostname with no flags.
